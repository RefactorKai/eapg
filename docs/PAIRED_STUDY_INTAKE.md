# Paired C++ study development intake

The metadata-only draw selected 12 PIE validation problems and 12 CppPerf projects before source or performance inspection. All 24 slots are retained below. This is an exploratory desk screen performed by one research agent on 18 November 2026 to refine the workload and support requirements. **Zero cases currently have confirmed eligibility.** Independent human review, intervention and measurement are still pending for all 24. All inspected problems and projects count as development exposure.

## Reproduce the draw

The fixed seed is `eapg-paired-development-2026-11-18-v1`. For each corpus, sort group identifiers by SHA‑256 of the compact UTF-8 JSON array `[seed, corpus, "group", group_id]`. Select the first 12 groups. Within each selected group, choose the first pair by hashing `[seed, corpus, "case", group_id + "/" + case_id]`. Break hash ties lexically by identifier. PIE uses corpus key `pie-validation`, group key `problem_id` and pair key `src_id::tgt_id`. CppPerf uses corpus key `cppperf-db`, the case-folded `owner/repo` group key and the new commit SHA as the case key. The algorithm uses pair identities only. Source compatibility, timing outcomes and adjudicability are observed after the draw.

**Feasibility witness for Railroad Trip.** Set city count and itinerary length to the same size (n) and alternate visits to the endpoints. Give every edge the tariff (A=3, B=1, C=2). The judge's bounds admit sizes (n=8,16,32,64,128,256). Every edge is crossed (n-1) times. The expected minimum fare is ((n-1)(n+1)=n^2-1). From source inspection, the target predicts ((n-1)^2) writes to the usage accumulator, and the reference predicts (3(n-1)) non-initialization writes when counting its two endpoint updates per trip plus one pass of prefix accumulation. This yields a concrete, independent count to test. The source pair replaces an algorithm instead of aligning an episode with each trip. It therefore exercises the study's support boundary and should remain a development case. [Original task specification](https://onlinejudge.u-aizu.ac.jp/problems/0614)

**Repeated-work control for UTF‑8 formatting.** Feed valid strings with identical code-point-width distribution and set precision proportional to total code-point count. Compare output bytes with an independent truncation oracle. The change removes a second walk through the accepted prefix while preserving a first walk. On the proposed width-one workload and proportional precision, both walk costs grow linearly in input length. The released timing-test names, `base_test.get_buffer` and `base_test.is_formattable`, supply no evidence that the timed path exercises this specific precision operation. ## What the desk screen establishes

- The preregistration draft can specify two physically available development frames and reproduce all 24 identifier selections. The metadata support two separate populations.
- Four PIE rows have a fixed input structure with no defensible in-contract size ladder. Several broader PIE algorithms have plausible scaling axes, but alignment, a canonical change list and a credible local restore must be demonstrated before eligibility.
- Two of 12 sampled repository patches carry any statistically significant improvement test in the CppPerf release. Five of 12 repository patches have multiple raw hunks. Raw hunk count excludes the LeetCode case where several changed statements lie within one printed hunk.
- This screen establishes neither a true positive nor a true negative for the confirmatory endpoint. The group counts are draw denominators. Human annotation time, group overlap beyond identifiers, clean-environment reproduction, runtime slopes and the recoverable-change fraction are unmeasured. A recruitment estimate should use independently confirmed yield rather than the number of promising source patterns.
